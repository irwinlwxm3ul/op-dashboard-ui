# Module spec: client-net

Owned paths: src/client/net/**, src/client/game/** and tests/client-net.test.ts

- MODULE: Client networking and game state (src/client/net, src/client/game) per ARCHITECTURE.md Stage B. Browser code, but keep core logic in pure classes testable in Node (no DOM in prediction/interpolation/clock modules).

- Transports (src/client/net): Transport interface {kind, send(msg: ClientMessage), onMessage(cb) -> unsubscribe, onClose(cb), close()}. WsTransport.connect(url?) default (location.protocol https -> wss) + location.host + /ws, resolves on open, rejects on error/timeout (8 s). LocalTransport: spawns a module Web Worker (new Worker(new URL("./localWorker.ts", import.meta.url), { type: "module" })) running src/client/net/localWorker.ts which on startLocal creates a MatchRunner (src/shared/sim, written concurrently — code against the contract) with one client (the local player), botDriverFactory = createBotDriver (src/shared/bots), and ticks runner.update(performance.now()) on a setInterval(…, 4) / timing loop; forwards ServerMessages to the main thread with postMessage and validates incoming messages with validateClientMessage. Same protocol as the network server so single-player exercises the full netcode path.

- Settings store (src/client/game/settings.ts): typed Settings (graphics quality low|medium|high|ultra, renderScale, fov (70-100, default 85), mouseSensitivity, adsSensitivity, scopeSensitivity, invertY, master/sfx/ui volume, showFps, damageNumbers, toggleCrouch, toggleAds, cameraMode default tpp|fpp, keybinds map action->KeyboardEvent.code, playerName), persisted in localStorage key dz.settings with defaults and validation, subscribe for changes.

- InputController (src/client/game/input.ts): pointer lock management (request on canvas click; exposes locked state), mouse look (sensitivity; ADS/scope sensitivity multiplier by current zoom; invertY; raw movementX/Y; pitch clamp +-89 deg), keyboard via rebindable keymap (defaults avoid browser-reserved Ctrl combos: WASD move, ShiftLeft sprint, KeyX walk (hold), Space jump, KeyC crouch, KeyZ prone, KeyQ/KeyE lean, KeyR reload, KeyF interact, KeyG throw frag, KeyH holster/fists, Digit1-3 weapon slots, Digit4 frag, KeyB swap weapons, Tab inventory, KeyM map, KeyV camera FPP/TPP toggle, AltLeft free look, Digit7 bandage/Digit8 firstaid/Digit9 medkit/Digit0 energy quick-use, KeyT refuel, F3 stats overlay, Escape menu; mouse left fire, right ADS (hold or toggle), wheel cycles weapons). In vehicles: W/S throttle, A/D steer, Space handbrake, Shift boost, F exit, Digit1-4 change seat (instead of weapon slots). In freefall/parachute: W dive, S slow, F open chute. Produces one PlayerInput per fixed tick (TICK_DT) with seq, mx/mz, base yaw/pitch, buttons, stance (toggle or hold crouch per setting; prone toggle), slot, rt (from ClientGame render time), actions queued from UI/keys (pickup/use/drop/enter/exit/seat/revive/jump/chute/throw/spectate/respawn/give). Free look: holding Alt rotates the camera only (expose cameraYaw/cameraPitch separately from aim). Also exposes edge events for UI (toggle inventory/map/stats/menu, camera toggle).

- ClientGame (src/client/game/ClientGame.ts) — the heart of client netcode: constructed with (transport, init: MatchInit, world: World (generateWorld(config.seed, kind)), settings). Clock sync: ping every 2 s, RTT smoothing, server-time offset estimation (min-filtered), renderTime = estimatedServerNow - INTERP_DELAY_MS (adapts slightly to jitter). Snapshot buffer (keep ~1 s) + interpolation of remote players (position lerp, angle lerpAngle, discrete fields from the newer snapshot), vehicles, projectiles; extrapolate up to MAX_EXTRAPOLATE_MS using velocity when starved; players missing from a snapshot (lower relevance rate) keep interpolating from their last two samples. Loot: map from MatchInit.loot + lootAdd/lootRemove deltas (apply in snapshot order). Events: typed event bus (on(type, cb)) delivering server GameEvents exactly once in order, plus LOCAL predicted events: localShot {weapon, origin, dirs, shotIndex, ballistic} emitted instantly when the local player fires (predicted), localReload, localDryFire, localLand, localJump, localFootstep {material, intensity} driven by predicted movement stride.

- Local prediction & reconciliation: the local player body (CharacterBody) is predicted every tick by running the shared physics stepCharacter/stepDrop with the same MoveIntent construction the server uses (replicate the GameSim rules for speedMul, sprint/ADS interplay, stance) — put this in a shared-friendly helper inside src/client/game (e.g. predictMovement) and keep it consistent with the sim spec in ARCHITECTURE/PLAN. Keep pending inputs; on each snapshot take self.ack, reset to the server body (pos, vel, onGround, airTime, jumpBuffer, fallSpeed, stance, mode) and replay unacked inputs; visual error smoothing: render position = predicted + decaying offset (so corrections are smooth, snap if error > 2 m). When the local player drives a vehicle predict the vehicle with stepVehicle similarly (reconcile from NetVehicle state); as a passenger interpolate. Plane mode: follow plane path from PlaneState (deterministic from time). Predicted weapon state: fire cadence (fireCooldown), mag count, reload timers, ADS blend, spray count and RECOIL (same recoilForShot/recoverRecoil functions as the server so the camera recoil matches the server-authoritative aim; softly blend toward server recoilPitch/Yaw from SelfState), shot directions (shotDirections with the same seed hash32(id, shotCounter)) so predicted tracers match the server. Server-confirmed hits only (hitmarkers come from server hit events).

- Interaction prompt resolution (client-side, for UI): nearest valid interaction for the local player: in plane -> jump (only when over map), freefall -> open chute, near downed teammate -> revive (hold), near vehicle -> enter (seat), near loot within INTERACT_RANGE and in view -> pickup (prefer the loot the crosshair points at), in vehicle -> exit. Expose as FrameState.interaction with a typed kind and target, and a method performInteraction() that queues the right action.

- FrameState (src/client/game/types.ts, export it): everything renderers/UI need per frame: time (render server ms), dt, phase, config, world, roster (Map id->RosterEntry), localId, viewTargetId (self or spectated player), self (LocalPlayerView: predicted body pos/vel/stance/mode, base aim and predicted recoil, eye position, life, health, boost, downedHp, armor, weapons, activeSlot, ammo, items, capacity, timers (reload/draw/use/revive progress), ads, vehicle/seat, parachuteOpen, stats, placement, killerId, spectating), players (Map id->PlayerView: interpolated pos, vel, yaw, pitch, stance, mode, life, team, weapon, flags, vehicle, seat, hp/dhp if teammate, gear, isTeammate, name, lastUpdate age), vehicles (Map id->VehicleView incl. predicted local vehicle), projectiles (Map), loot (Map id->LootItem), zone (ZoneState with timer counting down smoothly), plane (PlaneState + current plane position), alive, teamsAlive, ping, interaction, results (MatchResults when ended), training targets positions if training. ClientGame API: update(dtSeconds) (samples input on fixed ticks, sends, predicts, interpolates; call each animation frame), getFrame(): FrameState, on(type, cb), queueAction(action), dispose(); also aim access for the camera (aimYaw/aimPitch incl. predicted recoil, cameraYaw/cameraPitch incl. free look).

- Tests (tests/client-net.test.ts, Node env, no DOM): clock sync converges with simulated latency; interpolation between snapshots at renderTime; extrapolation cap; reconciliation: with simulated server applying the same inputs with 100 ms latency, predicted position equals server position after ack (no drift) and corrections are smooth; misprediction (server teleport) snaps after threshold; event bus delivers each server event once and in order across snapshots; loot deltas applied; predicted shot directions equal those computed by the shared items functions; interaction prompt picks the right target. Use stub transports.

## UPDATE (parallel build) — overrides conflicting points above
- `src/client/game/types.ts` is now a FIXED CONTRACT owned by the integrator (FrameState, PlayerView,
  VehicleView, LocalPlayerView, Interaction, ClientEvent/LocalEvent, ClientEventBus, Settings,
  SettingsStore, KeyAction, InputApi, ClientGameApi). Do not edit it; implement it exactly.
- Export from `src/client/net/index.ts`: `Transport`, `WsTransport` (static `connect(url?)`), `LocalTransport`
  (constructor spawns the worker; `start(config: MatchConfig, name: string)` sends startLocal).
- Export from `src/client/game/index.ts`: `ClientGame` (class implementing `ClientGameApi`; constructor
  `(transport: Transport, init: MatchInit, settings: SettingsStore)` — it generates the world itself with
  `generateWorld(init.config.seed, init.config.mode === 'training' ? 'training' : 'island')`),
  `settings` (singleton `SettingsStore`, localStorage key `dz.settings`), `InputController` (implements `InputApi`),
  `DEFAULT_KEYBINDS`, `predictMovement` helpers.
- The app controller (integrator) owns the flow: it creates the transport, waits for `matchInit`, then
  constructs `ClientGame`. `ClientGame` must therefore subscribe to the transport itself and handle
  `snap`, `pong`, `matchOver` messages (and ignore lobby messages, which the app handles).
- Free-look and FPP/TPP toggling: `FrameState.camera` (CameraInput). Pointer lock is requested by `InputApi.requestLock()`.
